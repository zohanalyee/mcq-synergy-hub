# GSC Page Indexing — Audit Report (no changes made)

All checks below were run live against the published site with a Googlebot user-agent, plus a read of the current source config.

## 1. www vs non-www (I-7) — correctly configured

| URL | Result |
|---|---|
| `https://mcqsai.com/` | 200 |
| `https://www.mcqsai.com/` | 301 → `https://mcqsai.com/` |
| `https://www.mcqsai.com/tools/pdf-compressor` | 301 → non-www equivalent |
| `https://www.mcqsai.com/mock-tests/junior-office-associate-bps-13` | 301 → non-www equivalent |

Canonicals on the non-www pages point at the non-www URL, so there is **no canonical/redirect conflict**. A single-hop 301 to the canonical host is exactly what Google expects.

"Page with redirect" (205 pages) is therefore **expected, not an error**: it is Google reporting the `www` variants (and other legacy/alias URLs it has on file) as redirecting. Redirecting URLs are never indexed by design — they are excluded, not broken. No validation fix is needed. `public/_redirects` is inert on Lovable hosting (Netlify convention only); the host performs the www 301.

## 2. The two "noindex" pages — live state contradicts GSC

Live HTML, Googlebot UA:

- `/tools/pdf-compressor` → 200, `<meta name="robots" content="index,follow">`, correct canonical.
- `/mock-tests/junior-office-associate-bps-13` → 200, `index,follow`, correct canonical, present in `sitemaps/mock-tests.xml` (37 URLs).

So neither page is noindex today. The GSC entries are **stale snapshots** from an earlier crawl (same conclusion as the earlier JOA check). The only `noindex` in `MockTestDetail.tsx` is the "test not found" fallback, and the thin-page gating applies only to `/boards/...` topic pages.

One genuine inconsistency worth a decision (not a bug affecting indexing today):

- Policy (`src/config/toolsSeo.ts` allow-list of 15 tools, mirrored in `scripts/generate-sitemaps.mjs`) says every other `/tools/*` page should be `noindex,follow`. Tools that render `ToolWrapper` obey this (verified: `/tools/qr-generator` → `noindex,follow`; `/tools/aggregate-calculator` → `index,follow`).
- But 8 tools listed in `TOOLS_WITHOUT_SEOHEAD` in `scripts/prerender-routes.mjs` — including `pdf-compressor`, `image-compressor`, `image-converter`, `pdf-merger`, `pdf-to-text`, `pdf-splitter`, `age-calculator`, `timer`/`units`/`notes` variants — do not use `ToolWrapper`, so they never emit a robots tag from React. `inject-meta.mjs` gives them static `index,follow` while `tools.xml` (15 URLs) excludes them.

Net effect: those pages are crawlable/indexable but absent from the sitemap — indexable orphans that conflict with the deliberate "thin utility tools are noindex" AdSense-safety policy. Two possible resolutions (your call, no change made):
- (a) Treat them as intentionally indexable → add real on-page depth + include in `tools.xml`.
- (b) Honour the allow-list → have `inject-meta.mjs` emit `noindex,follow` for tools outside `INDEXABLE_TOOL_PATHS`.

## 3. robots.txt — no real content page is blocked

Current rules block only: `/admin*`, `/test-session/*`, auth routes (`/auth`, `/signin`, `/signup`, `/complete-profile`, `/verify-email*`, `/reset-password`, `/forgot-password`), and query-parameter permutations `?count=`, `?timed=`, `?topic=`, `?difficulty=`, `?q=`, plus `/subjects?*`. `?lang=` is deliberately left crawlable.

Nothing in that list matches a clean content path — `/boards/*`, `/mock-tests/*`, `/tools/*`, `/p/*`, `/blog/*`, `/exams/*`, `/announcements*` are all allowed. The 657 "Blocked by robots.txt" URLs are almost entirely the parameterised practice-mode variants generated by internal links in `PracticeModeButtons.tsx`, `Subjects.tsx`, `SubjectContent.tsx`, `BoardTopicPage.tsx`, `SyllabusBuilder.tsx` and search (`?q=`) — i.e. duplicates of clean canonical URLs. Blocking them is intentional and correct.

Minor observation: because these parameter URLs are internally linked, Google keeps rediscovering them, which keeps the "Blocked" count high forever. If you ever want that number to shrink, the fix is link hygiene (`rel="nofollow"` or navigating via state rather than query strings), not a robots.txt change.

## Bottom line

- Item 1: correct as-is, "Page with redirect" is expected behaviour of the www 301.
- Item 2: both named pages are live `index,follow`; GSC data is stale. The only real issue is the tools allow-list vs `TOOLS_WITHOUT_SEOHEAD` mismatch — needs a policy decision.
- Item 3: no real content blocked; all 657 are intentional parameter duplicates.

No code, config, sitemap, or GSC state was changed, and AdSense "Confirm fixed" was not pressed.
